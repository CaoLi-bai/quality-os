# 项目介绍与面试追问

## 一分钟版本

> 我做了一个个人实践项目 QualityOS，目标不是用 AI 多生成用例，而是解决 AI 生成资产能不能可信进入测试交付的问题。它以已批准规格为事实源，把需求、风险、Oracle、用例、脚本和执行记录串成质量图谱。候选测试先经过独立审查，再在正确版本和故障版本上双向验证；失败保留第一次证据并分类，UI 自愈只能修改定位器，不能动断言或 Skip。最后输出 HTML 证据报告，但高风险资产仍需人工批准。项目还包含针对模糊需求、提示词注入和非法自愈的工作流自身评测。

## 三个最有区分度的点

1. **反假绿**：Good Build 通过不够，Fault Build 必须失败；Healer 无权改变测试意图。
2. **测试工作流自身被评测**：不是只评测被测 Agent，连规格生成、注入识别和自愈策略都有黄金任务与 pass^k。
3. **工程与业务结合**：用退款金额、幂等和越权证明质量门禁，不停留在通用 Todo Demo。

## 高频追问

### 为什么不用一个 Agent 全做完？

生成和审查如果共享推理上下文，容易形成自证。独立审查只拿规格、用例、候选和证据；最终放行仍由确定性代码负责。多 Agent 不是目标，决策权分离才是目标。

### 为什么不是完整变异测试？

当前是风险导向的四类显式故障注入，能够证明端到端机制，但覆盖范围有限。后续可以接 mutmut、PIT 或 Stryker，并增加等效变异人工判断。不能把小样本故障检出率说成 mutation coverage。

### 如何防止 AI 把 Bug 修成通过？

业务预期来自批准规格；原始与候选 AST 规范化后，除 locator 参数外任何差异都阻断。Skip、删除、断言和控制流变化均不能进入候选。合法候选也要重跑并人工审批。

### fixture 是不是伪 AI？

fixture 是明确标注的离线可重复执行器，用于验证工程闭环，报告写 `is_ai=false`。真实模型通过独立 provider 调用，不会失败时偷偷回退 fixture。模型效果和工程可运行性分开验证。

### 你的银行经验怎么体现？

金额用整数分，验证累计边界和最终状态；幂等不仅看响应，还检查是否重复入账；越权同时验证读和写；所有高风险歧义不由模型补规则。这些都是资金与合规测试方法向 AI 工作流的迁移。

## 必须主动说明的边界

这是个人实践，不是公司生产项目。当前故障类型、Playwright locator 范围和注入检测规则有限；在线模型效果、组织提效和线上收益需要另行测量。主动讲清楚边界不会减分，反而证明你理解质量证据。
